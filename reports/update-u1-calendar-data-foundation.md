## 6. Final JSON Schema

Documented in full in **`docs/calendar-data-schema.md`**. Summary:

```json
{
  "schemaVersion": "1.0",
  "calendarType": "study-planner-canonical-calendar",
  "year": 2026,
  "generatedBy": "tools/generate-calendar.js",
  "sourceOfTruth": { "calendarStructure": "...", "studyCycleMeaning": "...",
                     "planning": "...", "completion": "...", "progress": "..." },
  "studyCycle": { "startDate", "endDate", "totalDays", "totalWeeks",
                  "studyWeekLength", "startsOnWeekday", "endsOnWeekday",
                  "weeks": [...], "gradedDates": [...], "practiceDates": [...] },
  "months": [ { "month", "monthName", "daysInMonth", "firstDate", "lastDate",
                "firstWeekday", "studyCycleDates", "dates": [ … ] } ]
}
```

Per-date record fields: `date, year, month, monthName, day, weekday, weekdayShort,
weekdayIndex, isoWeekday, isoWeekdayIndex, dayOfYear, isStudyCycleActive, studyWeek,
studyDay, cycleDay, isStudyWeekStart, isStudyWeekEnd, isGradedDay, isPracticeDay, special,
specialLabel, notes, events`.

Example (cycle start):
```json
{ "date": "2026-10-02", "weekday": "Friday", "isStudyCycleActive": true,
  "studyWeek": 1, "studyDay": 1, "cycleDay": 1,
  "isStudyWeekStart": true, "special": "study-week-start",
  "specialLabel": "Study Week Start", "notes": [], "events": [] }
```

## 9. Study-Week Mapping

| Week | Start | End | Days | Boundary weekdays |
|---|---|---|---|---|
| W1 | `2026-10-02` | `2026-10-08` | 7 | Friday → Thursday |
| W2 | `2026-10-09` | `2026-10-15` | 7 | Friday → Thursday |
| W3 | `2026-10-16` | `2026-10-22` | 7 | Friday → Thursday |
| W4 | `2026-10-23` | `2026-10-29` | 7 | Friday → Thursday |

Matches the specification exactly. Boundaries are **derived** from the plans by the
generator, not hardcoded. `getStudyWeekDates(n)` returns the 7 canonical dates for each
week; an unknown week returns `[]` rather than a guessed range; adjacent-week navigation
is clamped to the real cycle (no wandering past W1/W4).

## 10. Study-Day Mapping

Study day = position **within** the study week (1–7), derived from the plan's
`dayNumber` (which is the cycle day 1–28) via `studyDay = dayNumber − (week−1)×7`. Both
values are exposed so no consumer must derive one from the other. Every week exposes
study days `[1,2,3,4,5,6,7]`; `studyDay 1` sets `isStudyWeekStart`, `studyDay 7` sets
`isStudyWeekEnd`. Cycle days run 1…28. Verified consistent for all 28 active dates.

**First week (matches the spec table):**

| Date | Week | Day | Special |
|---|---|---|---|
| 2026-10-02 | 1 | 1 | `study-week-start` ("Study Week Start") |
| 2026-10-03 | 1 | 2 | — |
| 2026-10-04 | 1 | 3 | — |
| 2026-10-05 | 1 | 4 | — |
| 2026-10-06 | 1 | 5 | — |
| 2026-10-07 | 1 | 6 | `practice` ("Practice Day") |
| 2026-10-08 | 1 | 7 | `graded` ("Graded Assignment") |

## 11. Graded-Day Metadata

Graded-ness is **derived from the authoritative plans** (any task with `type === 'graded'`),
never hardcoded and never assumed from "every 7th date". The four graded days:
`2026-10-08`, `2026-10-15`, `2026-10-22`, `2026-10-29` (each study day 7), each exposing
`isGradedDay: true`, `special: "graded"`, `specialLabel: "Graded Assignment"`. Practice days
(`10-07`, `10-14`, `10-21`, `10-28`) are marked separately. A test cross-checks both flags
against the plan tasks for all 28 dates, and confirms no non-graded date is marked graded.

Future UI identifies a graded date via `isGradedDay` / `special` — never "October 8 is graded".

## 12. Notes/Event Metadata

Every one of the 365 dates exposes `notes: []` and `events: []`, including inactive dates.
These are **empty placeholders** — U1 implements no note/event UI and invents no content.

## 15. Generator Changes

New `tools/generate-calendar.js` (14,845 bytes), following `tools/generate-plans.js`
conventions (`--check` mode, deterministic, no dependencies, read-only on sources).

- **Deterministic:** UTC-only math, no clock reads, no randomness, stable key order,
  2-space JSON + trailing newline. Proven byte-identical across repeated runs (test K1/K2).
- **Derives from authoritative plans:** reads `weekNumber`, `dayNumber`, and graded/practice
  task types from the 28 daily plans; never writes to them.
- **Fails loudly (exit 1) on inconsistent source data:** missing/duplicate study day, a week
  that is not exactly 7 contiguous days, a cycle gap, filename/date mismatch, wrong cycle
  boundaries, a week not starting Friday, or a year that does not total 365 dates.
- `--check` verifies the committed file matches a fresh generation (drift detection).

> **Real defect caught by the loud-failure design.** The generator's first run aborted with
> *"Study week 2 is missing study day 1"*. Investigation showed the plans' `dayNumber` is the
> **cycle** day (1–28), not the day-within-week (1–7). The generator now derives
> `studyDay = dayNumber − (week−1)×7` and validates that relationship, rather than trusting
> `dayNumber` to be a study day. This distinction is now documented and tested (G5).

## 21. Risks / Limitations

**LOW**
- The calendar covers **2026 only**. A future year needs a new generated file (the generator
  is parameterised by `YEAR` but currently hardcodes 2026); the access layer takes whatever
  document it is given.
- The `calendarFile` config key is present in `index.html` but **not yet fetched by the
  app** — U1 intentionally changes no runtime behaviour. U2 wires the fetch.
- Graded/practice markers reflect the *current* generated plans. If the planner output
  changes, `node tools/generate-calendar.js` must be re-run; `--check` (or the K1 test)
  catches drift.

**INFORMATIONAL**
- `studyDay` (within week, 1–7) and `cycleDay` (across cycle, 1–28) are distinct and both
  exposed to prevent the ambiguity that caused the generator's first loud failure.
- `special` has a fixed precedence (graded > practice > study-week-start > null); the
  booleans remain independent if a consumer needs to test conditions separately.
- `weekdayIndex` uses the repository's existing Sunday-based convention (0=Sun); ISO-8601
  Monday-based values are additionally provided as `isoWeekday` / `isoWeekdayIndex`.

No BLOCKER or HIGH risks. No scope was exceeded.

## 23. Final Verdict
